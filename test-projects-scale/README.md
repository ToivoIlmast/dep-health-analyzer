# Large-Scale Validation Corpus

This directory holds a small number of **large, generated** fixture projects used to validate
`dep-health-analyzer` at a scale [`test-projects/`](../test-projects/README.md) deliberately does not
cover - hundreds to ~10,000 modules - instead of only against `test-projects/`'s 33 small (mostly
under 30-module), shape-diverse fixtures.

**This is a sibling of `test-projects/`, not a replacement or a parallel system.** It reuses the exact
same generation/validation mechanism (`scripts/test-projects-toolkit.mjs`'s file-writing and git-commit
helpers, the same `dep-health.config.json`/`tsconfig.json` scaffolding, the same "each fixture is a
real standalone git repo" model) and lives in its own root directory specifically so that
`scripts/validate-test-projects.mjs`'s existing `readdirSync(test-projects/)` fixture-discovery loop and
`npm run test-projects:generate`'s existing runtime are completely unaffected - neither one gets slower
or has to know these fixtures exist.

## Fixtures

| Fixture | Modules | Cycles | Largest SCC | Purpose |
|---|---|---|---|---|
| `cycles-large` | 602 | 21 | 50 | **Main fixture for manually viewing the Graph** - realistic layered app, varied cycle shapes/sizes, one genuinely large SCC |
| `scale-medium` | ~2020 | 5 | 12 | Scalability/performance - several dependency-structure shapes at ~2000 modules |
| `stress-10k-acyclic` | ~10100 | 0 | - | Stress/performance - ~10000 modules, no cycles |
| `stress-10k-cyclic` | ~10100 | 8 | 34 | Stress/performance - ~10000 modules, with cycles |
| `regression-large` | 410 (HEAD) | 0 (HEAD) | - | Regression/history - a 10-commit sequence exercising `regression --baseline` and `history` at a few hundred modules |

Exact counts are only correct **right after regenerating** (`npm run test-projects-scale:generate`).
See "A note on module counts after viewing a report" below for why a fixture's own count can drift by a
few after you've generated an HTML report inside it.

### `cycles-large` - the fixture for manual visual inspection

602 modules: 20 core utilities, 15 shared modules, 30 plain (acyclic) feature areas (450 modules) for
realistic bulk, and 21 independent cycles of deliberately varied shape:

- 10 simple 2-node cycles, 5 three-node cycles, 3 five-node cycles, 2 eight-node cycles (one of the
  two eight-node cycles also has an extra internal chord, so it's a real SCC with more edges than a
  bare ring, not just a bigger ring).
- One 50-module ring - the fixture's one genuinely large SCC.

Every cycle has real external dependencies (each cycle's own first module calls out to a `shared`
module) and at least the big ring and the first small cycle also have a real external caller
(`area1/file0.ts` calls into both `bigring` and `cycle0`), so cycle members show real incoming AND
outgoing edges in the Graph view rather than being isolated islands. Cross-feature edges between the
plain areas are always one-way (a later area reaching into an earlier one), so nothing accidentally
bridges two intended-separate cycles into one bigger SCC.

Generated by `scripts/gen-scale-cycles.mjs` in 5 commits (baseline core/shared, plain areas, small
cycles, the big ring, final wiring) using the shared `writeChain()`/`closeRing()` helpers added to
`scripts/test-projects-toolkit.mjs` for this work.

### `scale-medium` / `stress-10k-acyclic` / `stress-10k-cyclic` - scale/performance fixtures

All three share one generator, `buildScaleFixture()` in `scripts/gen-scale-perf.mjs`, parameterized only
by total module count and a list of cycle ring sizes. Each mixes four different dependency-structure
shapes rather than one repeated pattern: independent leaf **core** utilities, a wide **flat** fan-out
area (many modules each depending on 1-2 core modules), several small **layered** feature areas (short
local chains off a shared/core module - the same general shape as `cycles-large`'s plain areas), and one
long **deep** chain (the opposite shape - narrow and long instead of wide and shallow). Optional cycles
are carved out as their own dedicated areas, same mechanism as `cycles-large`.

Each fixture gets a second, small "growth" commit (one more batch of flat modules, plus one new
cross-boundary reach from a flat module into `features/area0`'s internals) specifically so
`regression --baseline HEAD~1` and `history` have a real, non-empty, deterministic diff to analyze at
this scale, not just `cycles`.

- `scale-medium`: 2000 base modules, cycles of size 2/3/5/8/12.
- `stress-10k-acyclic`: 10000 base modules, no cycles - a pure scale/performance baseline.
- `stress-10k-cyclic`: 10000 base modules, cycles of size 2/2/3/5/8/13/21/34 - the same scale, with real
  cycle detection work to do.

### `regression-large` - regression AND history fixture

One fixture serves both roles, exactly the way `test-projects/history-laboratory` already does at a
~10-module scale - `regression-large` repeats that exact pattern (a deliberate, documented,
commit-by-commit sequence, each commit isolating one class of structural event) at a few hundred
modules instead of a few dozen. 15 core modules + 20-26 feature areas of 15 modules each (315-410
modules across the sequence), 10 commits:

1. Clean baseline.
2. Growth (3 more areas).
3. Introduce 10 cross-boundary findings (areas 0-9 each reach into a later area's internals).
4. Introduce a new cycle (`features/cycleA`, 4 modules).
5. Introduce a deep-internal finding (`area15` reaches 3 levels into `area16/internal/deep`).
6. Partial fix (5 of the 10 cross-boundary findings from commit 3 removed).
7. Fix (cycleA's ring is broken - the cycle is genuinely gone, not just unreached, matching
   `test-projects/cyclic-app`'s own established "break one ring edge" pattern for removing a cycle).
8. Growth (3 more areas).
9. A second, independent batch of 3 cross-boundary findings.
10. Fix (the batch from commit 9 is fully removed).

Uses `internalDepth: 2` / `deepInternalResidualDepth: 2` (matching this repository's own root config's
choice for its similarly-shallow `src/features/**`) so the deliberately-introduced findings actually
classify as cross-boundary/deep-internal instead of everything reading as "internal" by default.

Generated by `scripts/gen-scale-regression.mjs`.

## Regenerating the corpus

```bash
npm run test-projects-scale:generate   # regenerates all 5 fixtures
npm run test-projects-scale:validate   # correctness assertions + performance measurement
```

Or any single generator directly:

```bash
node scripts/gen-scale-cycles.mjs       # cycles-large
node scripts/gen-scale-perf.mjs         # scale-medium, stress-10k-acyclic, stress-10k-cyclic
node scripts/gen-scale-regression.mjs   # regression-large
```

Like `test-projects/`, nothing here is part of the npm package or production build - it's entirely
gitignored except this README, and excluded from this repository's own lint/typecheck/Jest run and
from `dep-health.config.json`'s own `exclude` list (see the root `.gitignore`, `eslint.config.cjs`,
`jest.config.cjs`, and `dep-health.config.json` - each has a `test-projects-scale` entry alongside its
existing `test-projects` one).

## Viewing the large cycles graph locally

```bash
npm run dev:cycle-map:large
```

This is the exact same command as the existing `npm run dev:cycle-map` (which points at
`test-projects/large-cycle-app`), just pointed at `cycles-large` instead - it builds the CLI and runs
`cycles --mode html` against it, using the **same production visualization code**, no special-cased
viewer for this fixture. Open the printed report path in a browser. You should be able to:

- See the **Full Graph** (all 602 modules, hierarchical layout).
- Click a cycle from the Findings list to see the **Focused Graph** - a real subgraph around just that
  cycle plus its 1-hop neighbors, not the whole 602-module graph.
- Find the 50-module `bigring` SCC (the largest one) and each of the 21 smaller, differently-shaped
  cycles.
- Use the minimap, zoom/pan, area filters, and cycle-edge highlighting - all identical to
  `dev:cycle-map`'s experience on `large-cycle-app`, just on a bigger, more varied graph.

`bigring`'s 50 members exceed the Focused Graph's `FOCUS_FULL_SCC_MAX` (40) threshold, so selecting it
falls back to the existing **representative cycle** view (a real 50-edge ring, not the full
neighborhood) - the same fallback `large-cycle-app`'s own 7-node ring never triggers (7 < 40), now
exercised at a scale where it actually matters. This is a pre-existing, documented characteristic of
the Focused Graph feature, not something specific to this fixture.

## Performance measurement

`npm run test-projects-scale:validate` measures (via `/usr/bin/time -v`) wall-clock time and peak RSS
for `cycles`, `regression --baseline HEAD~1`, and `history --points 2` on `scale-medium` and both
`stress-10k-*` fixtures, and **reports** the numbers rather than gating on an invented pass/fail
threshold - there is no established baseline to compare against, so a hardcoded "must complete in under
Xs" assertion would be arbitrary. See this repository's own change history / PR description for the
actual measured numbers at the time this corpus was added.

## A note on module counts after viewing a report

Running `cycles --mode html` (via `npm run dev:cycle-map:large`, `npm run dev:cycle-map`, or the CLI
directly) writes `reports/cycles.html` plus `reports/assets/*.js` (`dagre.min.js`, `cytoscape.min.js`,
`cytoscape-dagre.js`) into the target directory. Because dep-health-analyzer's file discovery isn't
scoped to `src/**` and these fixtures have no `exclude` entry for their own `reports/**`, those 3 fixed
asset files get picked up as extra "modules" (with no dependencies) on the *next* scan of that same
directory - inflating the reported module count by exactly 3 (e.g. `cycles-large` reads 605 instead of
602 on a second run). **This is a pre-existing characteristic of the analyzer itself, reproducible
identically on the already-existing `test-projects/large-cycle-app` fixture** (16 -> 19 after one HTML
report generation) - it is not introduced by this corpus and was deliberately left unchanged, per this
work's own scope (no analyzer semantics changes for the sake of these tests). It never affects cycle or
SCC counts (the asset files have no imports to resolve). Run `npm run test-projects-scale:generate`
before `npm run test-projects-scale:validate` for exact, uncontaminated counts - which is already the
natural order both scripts are meant to be run in.

## What was deliberately NOT done

- No new analyzer features, scoring, or rules were added to make these fixtures "pass" - they exercise
  existing `cycles`/`regression`/`history` behavior only.
- These fixtures are not part of `npm run test-projects:generate` / `npm run test-projects:validate` -
  keeping them a separate, opt-in step keeps the existing corpus's generation and validation exactly as
  fast as before.
- `stress-10k-acyclic` / `stress-10k-cyclic` intentionally have no dedicated `dev:cycle-map`-style
  browser-viewing command - rendering a 10000-node graph in a browser has no real diagnostic value over
  the CLI's own compact/full output, and would risk implying a claim ("this is viewable") that isn't
  useful in practice. `cycles-large` is the one fixture meant for manual visual inspection.
