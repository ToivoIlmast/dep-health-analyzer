# External Validation Corpus

This directory holds 33 small, realistic JavaScript/TypeScript fixture projects used to validate
`dep-health-analyzer` against a variety of real project shapes - frameworks, ecosystems, monorepo
layouts, and deliberately tricky dependency-graph structures - instead of only against the
synthetic unit-test fixtures under `src/**/__tests__`.

**These fixtures are validation environments, not architectural reference implementations.**
Fixture and directory names (e.g. `layered-app`, `messy-app`, `nightmare-app`, `same-directory-complex`)
describe the *shape* of a project's dependency graph - they are not a claim that the shape is
architecturally correct or incorrect, good or bad. `dep-health-analyzer` itself does not know what
your intended architecture is; neither does this corpus.

## What is and isn't here

- Nothing under `test-projects/` is part of the npm package or the production build. It is entirely
  ignored by git (`.gitignore`) except for this file and is regenerated on demand from the scripts
  in `scripts/gen-*.mjs`.
- Creating and validating this corpus did not change any production analyzer code, CLI behavior, or
  config schema (the one exception is the `.mts`/`.cts` discovery fix that this corpus's `mts-cts`
  fixture was built specifically to cover - see "Fixed via this corpus" below).
- It is also excluded from the repository's own Jest run (`jest.config.cjs`'s `modulePathIgnorePatterns`)
  and from lint (`eslint.config.cjs`'s `ignores`) - fixture package names like `@corpus/shared` would
  otherwise collide with each other across monorepo fixtures in Jest's module-naming ("haste") map,
  and fixture source files intentionally use CommonJS/browser globals this repository's own lint
  rules don't allow.
- Each fixture is a real, standalone git repository (its own `.git`, its own commit history) with a
  realistic `package.json`, `tsconfig.json` (where applicable), and `dep-health.config.json`.

## Regenerating the corpus

Fixtures are produced by small Node.js generator scripts, not hand-authored file by file, so the
whole corpus (or any single fixture) can be regenerated deterministically:

```bash
npm run test-projects:generate   # regenerates every fixture, then adds each fixture's README.md
npm run test-projects:validate   # runs machine-verifiable assertions against representative fixtures
```

Or run any single generator directly:

```bash
node scripts/gen-basic.mjs        # vanilla-js, vanilla-ts, node-commonjs, node-esm
node scripts/gen-frontend.mjs     # react-js, react-ts, vue-js, vue-ts, angular-ts
node scripts/gen-backend.mjs      # express-js, express-ts, nestjs-ts
node scripts/gen-fullstack.mjs    # nextjs-ts, vite-react-ts, vite-vue-ts, svelte-ts, astro-ts
node scripts/gen-libraries.mjs    # typescript-library, typescript-cli
node scripts/gen-monorepos.mjs    # monorepo-npm, monorepo-pnpm
node scripts/gen-structural.mjs   # layered-app, feature-oriented-app, flat-app, messy-app
node scripts/gen-stress.mjs       # cyclic-app, nightmare-app, large-cycle-app
node scripts/gen-traps.mjs        # same-directory-complex, deep-but-valid, cross-boundary-but-valid
node scripts/gen-mts-cts.mjs      # mts-cts
node scripts/gen-history-lab.mjs  # history-laboratory
node scripts/gen-readmes.mjs      # adds/refreshes each fixture's own README.md
```

All generators share `scripts/test-projects-toolkit.mjs` (file writing, git init/commit helpers,
`package.json`/`tsconfig.json`/`dep-health.config.json` scaffolding). Regenerating a fixture deletes
and recreates its directory from scratch, including its git history - the generator scripts are the
source of truth, not the files on disk. (This file, the top-level corpus README, is not itself
regenerated by any script - it is committed directly, alongside the generator scripts.)

## Running dep-health against a fixture

From the repository root, after building the CLI (`npm run build`):

```bash
node dist/app/cli.js regression --target test-projects/<name> --baseline HEAD~1
node dist/app/cli.js cycles --target test-projects/<name>
node dist/app/cli.js history --target test-projects/<name> --points <N>
```

Most fixtures need no `npm install` (they only reference `typescript`/framework type packages as
`devDependencies` for realism; the analyzer itself resolves relative imports without needing
`node_modules` present). Monorepo fixtures reference workspace packages by alias (`@corpus/*`) and
are the intended way to exercise the analyzer's bare-specifier alias resolution (see "Known
limitations" below for exactly what that does and doesn't cover).

## Machine-verifiable validation

`npm run test-projects:validate` (`scripts/validate-test-projects.mjs`) does two things:

1. **Smoke-checks every fixture** - runs `cycles`, `regression`, and `history` against all 32
   fixtures and confirms none of them crash or hit a config error (a real risk when a fixture's own
   generated `dep-health.config.json` is malformed - this has caught a real bug before).
2. **Asserts real observations on representative fixtures** - not just "the CLI didn't crash." See
   `scripts/validate-test-projects.mjs`'s assertions in its "Phase 2" section: cycle counts on
   fixtures with a known cycle (both present and absent), the `includeTypeOnlyImports` flip on two
   TypeScript fixtures, and structural invariants on `history-laboratory` (a cycle appearing and
   disappearing at specific commits, a type-only dependency appearing at another). Each assertion
   checks a specific commit resolved by its own commit message (via `git log --grep`), not just
   whatever the fixture happens to be at HEAD - `regression`'s own smoke-check baseline is resolved
   from the real "content HEAD" (skipping the trailing README-only commit every fixture ends with),
   not a blind `HEAD~1`, which for a fixture whose last commit is `gen-readmes.mjs`'s own README-only
   commit would silently compare a docs-only change against itself (an always-empty diff, since
   `.md` files are never scanned).

This is deliberately not a full integration-test framework - see `scripts/validate-test-projects.mjs`
itself for the exact list of what is and isn't asserted.

## What the corpus covers

- **Ecosystems / module systems:** plain ESM, CommonJS, TypeScript with `import type`, TypeScript's
  "nodenext" per-file `.mts`/`.cts` module-format overrides.
- **Frameworks:** React, Vue, Angular, Express, NestJS, Next.js, Vite (React/Vue), Svelte, Astro -
  in both JavaScript and TypeScript where the framework supports it.
- **Libraries/tooling:** a small npm-library-shaped project and a CLI-shaped project.
- **Monorepos:** npm workspaces and pnpm workspaces, each with a realistic root tsconfig.json (the
  standard TypeScript "project references" pattern) and per-package `tsconfig.json`.
- **Structural diversity:** layered, feature-oriented, flat, and "messy" (organically grown,
  inconsistent) layouts.
- **Graph stress:** a fixture whose history introduces and removes several distinct cycle shapes,
  a larger synthetic fixture combining a ring cycle, a high-fan-in hub module, a deep chain, and
  cross-directory fan-out (its own big ring is deliberately broken again before HEAD, as part of its
  own history-drift stress story - see its README), and a focused static fixture with a genuinely
  large (7-node) SCC, a cycle member with a large number of real external dependencies, and two
  independent cycles reachable from one shared caller.
- **Heuristic traps:** fixtures built specifically to probe assumptions the analyzer must not make -
  that same-directory implies no cycles, that path depth implies a violation, or that reaching across
  directories implies bad design.
- **Module-extension edge case:** `mts-cts` - a focused regression fixture for `.mts`/`.cts` file
  discovery (see "Fixed via this corpus" below).
- **History laboratory:** one fixture with an exact, documented 12-commit sequence, each commit
  isolating one class of structural event (add module, add dependency, introduce/remove cycle,
  type-only dependency, file move, cross-directory dependency, refactor, batches of change).

Every fixture's own `README.md` documents its purpose, structural characteristics, the history
events in its commit log, and the analyzer observations expected from it - phrased as observations
("a cycle should appear at commit N"), never as verdicts ("this fixture has bad architecture").

## Known, pre-existing limitations this corpus deliberately surfaces

These are documented, already-tracked characteristics of the analyzer, not bugs:

- **`.vue`, `.svelte`, and `.astro` files are never scanned.** `src/core/scanner/discover.ts` globs
  `.js/.jsx/.ts/.tsx/.mts/.cts`, none of which cover a single-file component's own extension. Any
  dependency edge that exists solely inside a `.vue`/`.svelte`/`.astro` file's template/script block
  is invisible to the analyzer. See `vue-js`, `vue-ts`, `vite-vue-ts`, `svelte-ts`, and `astro-ts`.
- **CommonJS `require()` calls are not resolved as dependency edges.** See `node-commonjs`.
- **Bare specifiers resolve only through the scanned root's own `tsconfig.json` `compilerOptions.paths`
  - never through node_modules/package.json resolution.** A real npm/pnpm workspace resolves
  `@scope/package` imports at runtime via node_modules symlinks, not via tsconfig `paths`, so a
  normal monorepo's cross-package imports are invisible to the analyzer even with an otherwise
  idiomatic root tsconfig.json (references-only, no `paths`) - **verified precisely**, including the
  counter-case: manually adding matching `paths` entries to that same root tsconfig.json does make
  those same imports resolve. See `monorepo-npm` and `monorepo-pnpm`'s own README for the exact
  before/after dependency counts.

## Documented, intentional behavior (not a bug)

- `relationClassifier.ts`'s `getRelation()` has a gap between its `internal` (`residualDepth <= 1`)
  and `deep-internal` (`residualDepth >= deepInternalResidualDepth`, default 3) bands: a dependency
  with `residualDepth` of exactly `2` (with the defaults) falls through to `cross-boundary` even when
  it shares a long common path prefix. This is explicitly documented in
  `docs/CONFIGURATION.md#thresholds`, including a worked example table showing this exact case and a
  dedicated section on why raising `deepInternalResidualDepth` can move a case *into* this gap. **This
  is not a bug** - an earlier draft of this corpus's own documentation mischaracterized it as one; a
  second independent audit confirmed the gap is intentional and thoroughly documented, and this
  repository does not treat it as a defect. See `deep-but-valid`'s own README for where it's
  reproduced.

## Fixed via this corpus

- **`.mts`/`.cts` files were not discovered as scannable source**, even though README's Import
  Resolution section already promised `.mts`/`.cts` support and `resolve.ts` already correctly
  mapped a `.mjs`/`.cjs` specifier to a real `.mts`/`.cts` file on disk. Because that file itself was
  never scanned, its own outgoing imports - including ones completing a real runtime cycle - were
  silently dropped: a project with a genuine `a.ts <-> b.mts` cycle reported `Cycles detected: 0`
  with exit code `0`. Fixed in `src/core/scanner/discover.ts` (added `.mts`/`.cts` to the discovery
  glob); no change was needed in `resolve.ts` or `extract.ts` (ts-morph already parses `.mts`/`.cts`
  correctly once given the file path). See the `mts-cts` fixture, which is a dedicated regression
  fixture for exactly this case, and `src/core/scanner/discover.test.ts` /
  `src/core/scanProject.test.ts` for the unit/integration-level regression tests.

## Known, minor, unfixed issues

- `generateAISummary.ts` prints `Server: undefined` in the "AI Configuration" banner when
  `features.regression.ai.host` is left unset, instead of showing the actual default Ollama host.
  Cosmetic; not fixed as part of this corpus's own scope.
